# LLM Gateway 完整能力全景

## 1. 什么是 LLM Gateway

LLM Gateway 是业务应用、Agent 与各类模型供应商之间的统一模型调用控制面。

它最重要的价值不是简单地代理 HTTP 请求，而是让业务只依赖稳定的模型别名和统一协议，同时由网关集中处理供应商差异、路由、可靠性、限额、成本和安全等问题。

通常可以把网关分为三个平面：

| 平面 | 主要职责 |
| --- | --- |
| 数据面 | 接收请求、鉴权、限流、选择模型、协议转换、调用供应商、流式回传、记录调用结果 |
| 控制面 | 模型目录、路由策略、租户和密钥、模板、预算、策略配置、灰度与回滚 |
| 运维面 | 部署、扩容、监控、告警、审计、容灾、升级和容量规划 |

## 2. 统一 API 与协议适配

### 2.1 统一入口

成熟的网关应提供稳定且向后兼容的调用协议，常见方案包括：

- 兼容 OpenAI Chat Completions API。
- 兼容 OpenAI Responses API。
- 兼容 Anthropic Messages API。
- 允许业务按供应商原生格式直接透传，便于使用供应商特有参数。

统一入口应屏蔽鉴权头、消息结构、流式事件、结束原因、工具调用和 usage 字段的差异，同时避免随意删除供应商特有能力。

### 2.2 协议适配

每个供应商或 API 协议都应通过 Adapter 隔离：

- 构造上游 URL、请求头和请求体。
- 转换模型 ID、消息、工具定义和多模态输入。
- 转换普通响应、流式事件、结束原因和 usage。
- 转换上游错误，并标记错误是否可重试。
- 处理供应商特有的 token 统计、缓存命中、推理 token 和工具调用增量。

Adapter 不应直接处理鉴权、限流、路由和日志等横切逻辑，这些能力应位于统一服务层。

### 2.3 支持的调用形态

- 同步文本生成。
- SSE 流式生成。
- 批量调用和异步任务。
- 工具调用、多轮工具结果和流式参数。
- 结构化输出，包括 JSON Object 和 JSON Schema。
- 图片、音频、视频等多模态输入输出。
- Embedding、Rerank 以及供应商提供的其他模型能力。

不同模型的能力并不等价。网关应通过模型能力表判断请求是否受支持，而不是把所有参数盲目透传给所有模型。

## 3. 模型目录与动态路由

### 3.1 模型目录

每个可调用模型至少应维护以下元数据：

- 对业务暴露的模型别名。
- 供应商、上游模型 ID 和 API 协议。
- 上下文窗口和最大输出长度。
- 是否支持流式、工具调用、结构化输出和多模态。
- 输入、输出和缓存 token 的价格。
- 服务区域、数据合规属性和可用状态。
- 每分钟请求数、每分钟 token 数和并发能力。

### 3.2 路由策略

网关可根据以下条件动态选路：

- 请求中的模型别名。
- 租户、应用和业务场景。
- 主备优先级。
- 加权流量和灰度比例。
- 成本、延迟和模型能力。
- 供应商健康状态与区域。
- 数据驻留和隐私策略。
- 影子流量、A/B 实验和降级策略。

路由应具备稳定、可解释和可回滚的行为。请求实际使用哪个模型，必须能在响应元数据或调用记录中查到。

## 4. 鉴权、租户与密钥管理

成熟网关需要支持：

- 面向业务应用的 Gateway API Key。
- 租户、项目、应用和环境隔离。
- 基于角色和权限的模型使用控制。
- 调用方密钥哈希存储、创建、禁用和轮换。
- 供应商密钥集中托管，不暴露给业务。
- 供应商密钥加密存储和定期轮换。
- 按模型白名单限制应用可访问的供应商。
- IP 白名单、来源限制和审计。

Gateway Key 与供应商 Key 必须分离。业务不应知道或依赖任何供应商凭证。

## 5. 可靠性

### 5.1 超时和重试

- 区分连接超时、读取超时、首字节超时和总超时。
- 只对连接失败、超时、上游限流和部分 5xx 错误重试。
- 使用指数退避和随机抖动，避免重试风暴。
- 限制最大重试次数和最大总耗时。
- 对具备幂等能力的上游请求携带幂等键。
- 流式响应已经向客户端发送内容后，不进行不可见的跨供应商重试。

### 5.2 故障隔离和降级

- 按供应商、模型和区域维护熔断器。
- 支持主模型失败后切换到备用模型。
- 支持按业务优先级降级到更便宜的模型。
- 过载时主动排队、背压或快速拒绝。
- 使用并发上限控制单个供应商和在途请求数量。
- 对资源紧张场景提供降级响应和明确的 Retry-After。

### 5.3 流式可靠性

- 正确转发 SSE 数据块和结束事件。
- 处理客户端断开连接并释放上游连接。
- 在客户端断开后停止持续计费的上游生成。
- 将不同供应商的流式事件转换为统一格式。
- 在流结束或最后一个 usage 事件中补齐 token 统计。

## 6. 限流、配额与成本治理

### 6.1 限流

- 按租户、项目、API Key、模型、供应商和 IP 限流。
- 支持 RPM、TPM、每日 token、并发数和请求突发量限制。
- 支持公平限流，避免一个租户耗尽全部共享容量。
- 对上游容量和本地客户端分别设置限流。
- 超限返回 429，并提供重试时间。

### 6.2 配额和预算

- 支持日、月、项目和组织级预算。
- 请求前估算成本并预留预算。
- 请求后依据实际 usage 结算。
- 支持软阈值告警和硬阈值拒绝。
- 支持供应商账单与实际调用记录的核对。

### 6.3 成本优化

- 根据输入长度、任务复杂度和预算选择模型。
- 支持 prompt cache 透传。
- 支持供应商侧缓存命中统计。
- 支持精确响应缓存；语义缓存应谨慎启用。
- 支持批量调用和异步任务以降低单位成本。

缓存必须有租户隔离、模型版本、Prompt 版本、参数和有效期约束。个性化或包含敏感信息的响应不应默认共享缓存。

## 7. Prompt 与版本管理

完整网关通常提供 Prompt Registry：

- 按名称、业务域或应用存储 Prompt 模板。
- 模板版本不可变，每次修改产生新版本。
- 支持变量定义、必填校验和安全替换。
- 支持按固定版本或稳定别名引用模板。
- 支持发布、回滚、灰度和实验。
- 记录一次调用实际使用的模板名称与版本。
- 防止模板变量泄露密钥或未授权上下文。

Prompt 模板版本必须进入调用元数据，否则无法解释线上输出差异，也无法完成效果回滚。

## 8. 输出约束与安全合规

- 支持 JSON Object、JSON Schema 和业务对象校验。
- 对不支持原生结构化输出的模型进行 Prompt 约束和后置解析。
- 工具调用参数必须经过 schema 校验。
- 支持输入和输出内容审核策略。
- 支持 PII 检测、脱敏、阻断或转人工。
- 支持敏感词、业务政策和模型白名单。
- 支持数据驻留、区域路由和供应商合规属性。
- 支持安全审计和策略变更记录。
- 避免在日志中默认记录完整 Prompt、响应和凭证。

内容安全策略应可插拔，不能与某一个供应商协议强耦合。

## 9. 可观测性

每次调用至少应记录：

- Request ID、Trace ID 和租户标识。
- 请求模型、实际模型、供应商和协议。
- 入口参数的关键特征，不默认记录完整内容。
- 输入 token、输出 token、缓存 token、推理 token 和总 token。
- 首 Token 延迟 TTFT、上游耗时、重试耗时和总延迟。
- HTTP 状态、统一错误码、上游错误码和结束原因。
- 重试次数、fallback 次数和限流结果。
- 单次成本、累计成本和预算状态。
- Prompt 名称与版本。

指标和日志之外，还应提供：

- 按模型、供应商和租户的聚合视图。
- 可用性、错误率和延迟分位数。
- 成本趋势和异常检测。
- 调用链路追踪和供应商故障定位。
- 审计日志与告警。

## 10. 配置与控制面

成熟网关应具备：

- 模型目录、路由规则和限流规则的集中管理。
- 配置版本化和变更审计。
- 配置校验、热更新和原子回滚。
- 管理 API 或管理后台。
- 环境隔离和发布流程。
- 灰度、金丝雀和影子流量。
- 密钥生命周期管理。
- 配置变更与调用结果之间的可追溯关系。

配置文件适合单机和学习项目，生产环境通常需要数据库与独立的控制面。

## 11. 部署与运维

- 无状态数据面实例，可水平扩容。
- 健康检查和优雅停机。
- 多实例之间的分布式限流和配额。
- 多区域部署、故障转移和容量规划。
- 上游供应商连接池和资源隔离。
- 数据库备份、恢复和配置灾备。
- 版本发布、回滚和兼容性测试。
- 压测、容量评估和故障演练。

## 12. 测试与兼容性

完整网关需要覆盖：

- 不同协议的请求和响应转换测试。
- SSE 流式事件顺序、增量内容和结束事件测试。
- 工具调用和多轮消息测试。
- JSON Schema 校验测试。
- 超时、重试、退避、熔断和 fallback 测试。
- 限流、配额和并发测试。
- 供应商错误码转换测试。
- 客户端断开连接测试。
- 配置热更新和回滚测试。
- 供应商真实调用 smoke 测试。
- 负载测试和长时间稳定性测试。

外部供应商不能作为唯一测试依赖，核心协议和韧性逻辑应使用可控制的 mock 上游验证。

## 13. 网关边界

LLM Gateway 通常负责模型访问和调用治理，不负责：

- Agent 的任务规划、循环控制和工作流编排。
- Agent 的长期记忆和业务知识库管理。
- 业务工具的权限判断和实际执行。
- 业务 Prompt 的业务决策逻辑。
- 业务应用自己的用户会话和产品状态。

Prompt Registry、内容安全和工具 schema 校验可以放进网关，但 Agent Runtime 和业务编排仍应保持独立，避免网关演变为难以维护的“大单体”。

## 14. 合理的演进顺序

1. 单协议代理和统一错误格式。
2. 双协议 Adapter 和动态模型路由。
3. 流式、结构化输出和 Prompt 版本管理。
4. 调用记录、Token、TTFT 和成本统计。
5. 超时、重试、fallback 和熔断。
6. 按租户、模型和供应商限流。
7. 密钥管理、缓存、配额和安全策略。
8. 灰度、控制面、多实例和多区域。

完整网关不等于把所有能力一次做完，而是确定清晰边界后，按可验证的纵向能力逐步演进。
